# Eleven Ways to Check If an AI System Is Correct

This week has 11 papers. Each paper checks, verifies, or measures the reliability of an AI system in a concrete way. A study rewrites real paper reviews with different rhetorical framing and finds AI reviewers reward polish over substance. Another paper tests how instruction tuning changes a model's stated confidence, and finds the confidence becomes less trustworthy even when accuracy barely moves. A fault-injection method validates AI-modernized scientific code by injecting the same hardware fault into the old and new versions and comparing the results. A Bayesian stopping method named optstop tells an evaluation exactly when it has already collected enough evidence, cutting wasted test runs. A four-axis benchmark tests AI judges on accuracy, robustness, and calibration, and finds a top judge model loses nearly 50 points of accuracy under a simple manipulation. A verification layer named RCV estimates when a safety classifier's decision is wrong and flags when the real world has shifted away from its training data. An architecture named the trusted kernel makes a text-to-SQL system structurally unable to invent a number. A claim-checking system named CLAIR-Fin breaks a financial answer into small pieces and checks each piece against evidence before trusting it. QuoteBench replays the same AI output through two different execution paths and finds a benchmark's pass/fail score can hide a large, real failure. Vero requires AI-written code to come with a machine-checked proof of correctness, and finds even the best AI agents solve barely half the test cases. A last method generates a formal specification for a program using only its test results, without ever reading the source code.

**[How Can Rhetoric Reward-Hack AI Reviewers?](https://huggingface.co/papers/2608.08975)** — An AI reviewer can score a paper based on how the paper sounds, not just what the paper says. This paper tests that exact risk. The researchers took real submissions to a top AI conference. They rewrote each paper along six separate rhetorical dimensions. One dimension is how strongly the paper frames its own evidence. One dimension is how the paper claims novelty. The underlying scientific content stayed the same across every rewrite. This process produced 4,200 different versions of the same papers. Five separate AI reviewers then scored every version. The validation contribution is this: a controlled test that isolates rhetorical style from real content, and measures how much style alone moves a review score. Evidence framing and novelty framing caused the largest score swings. A paper with a low starting score tended to rise under one framing. A paper with a high starting score tended to fall under a different framing. Telling a reviewer to be "strict" lowered every score, but did not fix this swing. The result is a documented weakness in AI peer review: an AI reviewer can reward polish over substance.

**[Are You Sure You're Sure? On the Impact of Instruction Tuning on Confidence and Lexical Diversity](http://arxiv.org/abs/2608.13430v1)** — Instruction tuning is an extra training step. This step teaches a raw language model to follow instructions well. This paper asks what instruction tuning does to a model's confidence. The researchers compared matched pairs of models: one before instruction tuning, one after. They tested the models across several question-answering tasks. They measured three separate things: accuracy, stated confidence, and calibration. Calibration means how well a model's stated confidence actually matches its real correctness rate. The uncertainty-quantification contribution is this: instruction tuning reliably changes a model's confidence level, even in cases where accuracy barely changes at all. Calibration measurably gets worse after instruction tuning. The paper also checks the variety in a model's wording. The variety between different possible explanations shrinks after instruction tuning. These results hold even after the researchers control for which answer the model picked. The conclusion is a warning: a user should not treat an instruction-tuned model's stated confidence as a reliable signal of correctness.

**[Validating LLM-Modernized Scientific Software Through Differential Fault Injection](http://arxiv.org/abs/2608.14527v1)** — An AI system can modernize old scientific code. The new code can look correct on every normal test. The new code can still behave differently from the old code under a rare fault, for example a hardware glitch or a rounding error. This paper builds a method to catch that exact gap, called differential fault injection. The method adds monitoring points at twelve locations inside a real quantum-chemistry software package. It then injects the same artificial fault into both the old code and the new, AI-modernized code, and compares the two responses. The validation contribution is this: the method ran over 2,200 test runs, including 200 directly paired fault injections, and the old and new code agreed in every paired case — a real, positive validation result, not just a normal test pass. The fault injections also found real hidden problems. The problems include a deadlock that only appears during certain execution phases. The problems also include a convergence failure under reduced numerical precision. The lesson is clear: a normal correctness test is not enough for AI-modernized scientific code. Fault-injection testing catches failure modes that normal testing misses.

**[Knowing When to Stop: Bayesian Optimal Stopping for LLM Evaluations](http://arxiv.org/abs/2608.14425v1)** — A standard AI evaluation tests every benchmark question the same fixed number of times. This wastes effort once an estimate is already precise. This paper builds a method named optstop for this exact problem. Optstop uses a Bayesian approach: it updates a belief about a result as new evidence arrives, instead of waiting for a fixed amount of evidence first. Optstop decides, question by question, when enough evidence has built up to stop testing that question. It spends more testing effort where the result is still uncertain, and less effort where the result is already clear. The method works for yes/no questions, ranked questions, and numeric-score questions. The uncertainty-quantification contribution is this: optstop treats "how much testing is enough" as a question of uncertainty, not a fixed budget. Across nine test settings, optstop cut planned test runs by 57 to 97 percent. It reached the same overall conclusions as running the full, fixed-size evaluation.

**[A Four-Axis Trustworthiness Benchmark for LLM-as-Judge in Principle-Based Regulation](http://arxiv.org/abs/2608.14329v1)** — An AI judge model can score whether a financial product follows a broad rule. An example broad rule is "be fair, clear, and not misleading." A rule like this resists a simple yes/no check. This paper builds a benchmark named Principle-Bench for this exact problem. Principle-Bench uses 168 realistic cryptoasset scenarios, each mapped to a real UK financial regulation. It scores an AI judge on four separate axes: accuracy, robustness to paraphrasing, robustness to manipulation, and calibration. The validation contribution is this: a benchmark that checks whether an AI judge stays reliable under pressure, not only whether it is accurate on ordinary inputs. The headline result is stark. A top AI judge model scored 74 percent accuracy on ordinary inputs. The same model's accuracy dropped to 27 percent once the input contained manipulative keywords — a drop the paper calls "compliance theatre." The paper also builds an audit tool named Ceca, which gives a counterfactual explanation for a score, not just a bare number. The conclusion: a team must report an AI judge's manipulation risk and calibration, not only its accuracy.

**[Regime-Conditional Verification: Correctness Estimation for Adapting and Monitoring Safety Classifiers](http://arxiv.org/abs/2608.14089v1)** — A safety classifier flags harmful AI output. It is trained on one definition of "unsafe," but a deployer often needs a different, more specific definition. A safety classifier's accuracy also quietly decays as real-world traffic changes over time. This paper builds a method named RCV, short for Regime-Conditional Verification, for both problems. RCV adds a lightweight layer on top of an existing safety classifier, without needing to retrain the classifier itself. RCV examines the classifier's internal signals and estimates the probability that a given prediction actually breaks the deployer's real policy. The verification contribution is this: RCV corrects predictions it judges unreliable, and separately, it detects when real traffic has shifted away from the classifier's training data, without needing new labels for that traffic. On three existing safety classifiers and two datasets, RCV recovered up to 81 percent of unsafe content the original classifier had missed. In a live deployment test against ten real attack campaigns, RCV detected every one, and resolved most of them through its lightweight correction alone, without a full retrain.

**[Never the Number: Structural Abstention for AI Systems Whose Answers Are Consumed as Fact](http://arxiv.org/abs/2608.13926v1)** — An AI system can turn a plain-language question into a database query. A system like this can silently invent a number that looks like a real answer. This paper builds an architecture to make that failure structurally impossible, not just less likely, called the trusted kernel with a generative shell. The rule behind the architecture is simple: the AI part of the system can influence which question gets answered, but it can never influence which value comes back as the answer. A separate, non-AI kernel matches a fully specified question against a fixed, limited set of answerable question forms, then compiles a matched question directly into a database query. The verification contribution is this: if a question does not match an answerable form, the system declines to answer, and this refusal needs no confidence score to trigger, because it is a structural fact, not a statistical guess. The pattern was tested across three domains and in a two-year real production deployment, against other systems including fine-tuned parsers and tool-retrieval agents. The goal is a system that cannot fabricate a number, not a system that fabricates a number less often.

**[CLAIR-Fin: An Adversarial Multi-Agent Framework for Claim-Level Verification and Adaptive Debate in Cross-Modal Financial QA](http://arxiv.org/abs/2608.13706v1)** — An AI system can answer a financial question with a wrong number, and a wrong number in a financial answer carries real financial consequences. This paper builds a system named CLAIR-Fin to catch this exact problem. CLAIR-Fin breaks a single AI answer into small, individual claims, and tracks every claim in a typed ledger, instead of checking the whole answer as one block of text. It assigns a different trust level to evidence depending on the type of claim being checked, and runs a grounding check between the drafting stage and the review stage of an answer. The verification contribution is this: when two AI agents disagree about a claim, CLAIR-Fin escalates the claim into a structured debate between the agents, and it separates claims that were actively checked from claims nobody challenged, through a measure named the Hallucination Risk Index. CLAIR-Fin can also abstain and refuse to answer when the evidence is genuinely not enough. On a 500-question financial benchmark, this approach raised a faithfulness score from 0.780 to 0.889. It abstained on 5.4 percent of questions rather than guessing, beating other retrieval-based methods on the same benchmark.

**[QuoteBench: How Matched Scores Can Hide Command-Path Failures](http://arxiv.org/abs/2608.13547v1)** — A coding-agent benchmark often scores success by checking only the final state after a command runs. A score like this can miss a broken command hidden in the pipeline underneath. This paper builds a benchmark named QuoteBench to expose this exact blind spot. QuoteBench uses 56 tasks drawn from 14 real, incident-derived task families. It replays the exact same AI-generated output twice: once through the normal execution path, and once through a strict parser that does not silently fix small quoting errors. The validation contribution is this: comparing these two replays reveals failures a single pass/fail score would hide completely, since the AI model's output never changes between the two runs. Success rates dropped between 55.4 and 73.2 percentage points between the two replays. In one case, an overall score barely moved, a gap of only 3.6 points — but underneath that stable score, 64.3 points of real damage were being canceled out by 60.7 points of accidental compensation elsewhere in the pipeline. The paper's conclusion: a benchmark score is a property of the full pipeline, not of the AI model alone.

**[Vero: Can AI Agents Build Formally Verified Software Repositories?](http://arxiv.org/abs/2608.13522v1)** — An AI coding agent can write code that looks correct. Looking correct is different from having a mathematical proof of correctness. This paper asks if an AI agent can produce both at once. It builds a benchmark named Vero for this exact question, using 43 real, multi-module test cases pulled from real code repositories. The test cases cover hard domains, including cryptographic protocols and distributed systems, restructured with a clear interface and a formal, machine-checkable specification. The verification contribution is this: an agent must produce code paired with a proof, checked by a formal proof system, not just code that passes a normal test suite. Vero also includes an audit mechanism that lets an agent flag a benchmark case where the official specification is actually impossible to satisfy, or where the official reference code is wrong. The best AI agent tested solved only 27 of the 43 cases, and failed completely on the hardest, most realistic repositories. The result is a difficult, honest testbed for measuring genuine, machine-verified correctness in AI-written code.

**[Can Formal Specifications Be Synthesized from Tests Alone?](http://arxiv.org/abs/2608.13240v1)** — A formal specification is a precise, machine-checkable description of what a piece of code should do. It is valuable for verification, but expensive to write by hand. Most AI methods for generating a formal specification need to read the program's actual source code, which is often impossible for proprietary software. This paper builds a method that skips that requirement entirely. It generates a formal specification using only a program's test suite and its execution traces, and never reads the program's implementation. The verification contribution is this: the method checks its own generated specification using bounded model checking, a technique that exhaustively checks a specification against a limited number of program states, then feeds the checker's feedback back into the generation process in a repeated loop. The method was tested on a benchmark named SpecGenBench, which targets Java Modeling Language specifications. The early results are encouraging, though turning checker feedback into something the AI model can actually use remains a real, unsolved challenge. The contribution is a privacy-preserving route to formal, verifiable specifications, without needing access to proprietary source code.
